# Workspace reader

Current interface rules are in `DESIGN_RULES.md`. They supersede conflicting styling details below and in `DESIGN.reference.md`; that reference remains a record of the source screenshot.

Direction: a document-focused developer portal using shadcn/ui. The sidebar keeps its warm off-white paper-and-ink appearance; workspace main content uses a cool light-gray canvas, white cards, dark ink, fine borders and a scoped blue action accent. Corners stay near 8px. System sans keeps interface text familiar; monospace is reserved for request URLs and bodies. No decorative assets or unlabeled sample data.

Theme tokens are semantic and complete: foregrounds are defined separately for cards, popovers, secondary surfaces, accents, and the sidebar; inputs and borders have their own values. `.workspace-content` uses canvas `#F4F6F8`, card `#FFFFFF`, ink `#242B35`, primary blue `#1877E8`, pale blue selection `#E8F1FF`, and border `#DFE4EB`. It scopes these colors plus green/amber/red status colors without recoloring the warm sidebar. HTTP method badges use green for GET, blue for POST, amber for PUT/PATCH, and red for DELETE. Both the shared shell and workspace content have matching dark token sets.

Sidebar follows the reference's grouped workspace navigation. Before a workspace is selected, it lists All workspaces and the user's accessible workspaces. Selecting a workspace switches to Overview, API (Collections and History), Design (UI · Stitchkit and Database · DBDesign), Project, Team, and owner-only Settings. In the compact desktop rail, API and Design open a popover with their destinations; in the expanded sidebar they show nested items. Breadcrumbs show the current workspace and section and link back to the directory or workspace overview. Design and Project show a clear coming-soon state while those existing portal flows are ported. The brand mark uses the product's three-stroke symbol, and the All workspaces control returns to the directory. Desktop search sits in the expanded sidebar when it applies; mobile keeps search in the page toolbar while the sidebar opens as a drawer. Icons identify folders, documents, navigation and actions. Badges identify actual HTTP methods, workspace roles, and unavailable sections. Tables keep workspace and membership data scannable. Mobile sidebar uses shadcn's sheet.

Workspace main content follows the dashboard composition documented in DESIGN.reference.md: a clear section title and readable explanation, then four compact summary cards and a wide work area beside a narrower supporting panel. The breadcrumb carries workspace context so the page heading can stay focused on the current section. The directory summary uses loaded workspace and role data; a workspace summary uses actual folder/request counts, role and update date. The main directory stays a table; collection requests stay browsable rows. The request detail pane groups path and query parameters, headers, authentication, and request body under Request; Responses shows saved status codes, schemas, and examples; Documentation shows the endpoint description and deprecation notes. Secret values are masked. Empty collections offer a clearly labeled local sample preview that is never sent to the server. At narrow widths, summary cards and content panels stack. The cool canvas and blue action accent are scoped to `.workspace-content`, so the sidebar keeps its existing theme. Approval queues, agent prompts, running-task progress and agent tiles are not target features and are omitted.

The Members tab preserves the workspace access flow: owners can add an existing account, change non-owner roles, remove members, and cancel pending invitations; non-owners can leave their own workspace. Each action uses the existing workspace API and asks for confirmation before access is removed.

Owners also get Settings to rename or delete the workspace. Deletion requires typing the workspace name and explains that synced documentation will be removed. Other roles do not see Settings.

Authentication uses the same neutral tokens with a centered product mark and name, a screen-specific heading, a compact form card, and a muted product note below it. Login, account invitation, workspace invitation acceptance, password reset, pending, error and success states remain connected to the existing API flow. A workspace invite asks the user to sign in with the invited account before accepting. The password visibility control is accessible by keyboard. Remember-me and policy links are omitted because the app has no matching session option or legal destinations.

Energy 2 / rhythm 2 / motion 1. Content carries the hierarchy; no gradients, glass, decorative patterns or marketing statistics.
